版本：V1.0 · 日期：2026-10-24 · 定位：正式工程的目录、职责、开发步骤与交付标准。

当前方向：**安卓个人使用、全部核心数据保存在本机、无需账号或服务器**。采用 **Kotlin + Compose + Room + DataStore**，一个 `app` 工程模块，内部按功能分目录。

配套阅读：[完整功能与数据模型设计 V2.0](个人生活管理App_完整功能与数据模型设计_V2.0.md)、[技术与存储方案](安卓本地版技术与存储方案.md)。功能字段以 V2.0 为准；安卓本地实现方式以技术方案和本文为准；旧三栏原型不限制完整功能范围。

AI 接手入口：[项目指引](../AGENTS.md)、[执行说明](ai/AI开发执行说明.md)、[任务与交接](ai/开发任务与交接.md)。视觉以 [UI/UX V3](iOS风格安卓UI与UX动效设计_V3.md) 和设计变量为准；研究与历史资料已分目录，见 [文档索引](README.md)。

### 2.1 各层只负责什么

| 位置 | 负责 | 约束 |
| --- | --- | --- |
| `feature/*` | 页面、表单、筛选、用户操作和状态 | 页面不直接读写 DAO 或磁盘 |
| `domain/usecase` | 多步骤、跨模块或多处复用的操作 | 简单列表查询不强行增加一层 |
| `data/repository` | 业务查询、保存、事务入口、模型转换 | 对外不暴露可任意写入的 DAO |
| `data/local` | 数据结构、SQL、事务和迁移 | 不包含页面与弹窗 |
| `data/files` 等 | 文件、备份、提醒等平台实现 | 不保存另一套财务事实 |
| `core` | 纯规则和跨模块基础类型 | 不依赖某个功能页面 |
| `app` | 应用组装和导航 | 不承载记账、周期等业务算法 |

仓库可采用 `TaskRepository.kt` 接口与 `LocalTaskRepository.kt` 实现；只有确实需要替换或隔离实现时再拆接口。简单对象不为每张表重复创建完全相同的三套模型。财务命令、页面状态、数据库实体和备份对象需要明确区分。

手动依赖注入由 `AppContainer` 集中管理，数据库和 DataStore 各保持单实例；Worker、Receiver 从同一容器取依赖。将来维护成本明显上升时再整体评估 Hilt，不混用两套依赖组装方式。[Android 架构建议](https://developer.android.com/topic/architecture/recommendations)

以任务为例，其余功能沿用相同命名习惯，按实际复杂度增减：

```text
feature/plans/task/
├─ TaskListRoute.kt                  取得 ViewModel、订阅状态、连接导航
├─ TaskListScreen.kt                 显示列表，接收状态和操作回调
├─ TaskListViewModel.kt              筛选、完成任务、加载和错误状态
├─ TaskListUiState.kt                列表状态定义
├─ TaskEditorRoute.kt                编辑页组装
├─ TaskEditorScreen.kt               编辑表单
├─ TaskEditorViewModel.kt            草稿、校验、正式保存
├─ TaskEditorUiState.kt              输入值、字段错误、保存状态
```

`Route` 处理页面接线，`Screen` 负责展示，`ViewModel` 管理页面状态。简单的静态页可以合并 Route 与 Screen；共用组件被多个功能使用后再移到 `ui/component/`，不要为了文件数量拆分。

## 4 数据库、设置与文件

### 4.1 数据层按领域对应

`entity/`、`dao/`、`repository/` 使用相同的领域分组，便于从功能查到数据实现。下表是完整逻辑覆盖范围，数据表按开发阶段逐步落地。

| 领域目录 | 对应模型与数据 | 关键实现 |
| --- | --- | --- |
| `profile/` | LocalProfile、首页卡片、快捷入口、功能开关 | 建立本地 owner；不建设登录 |
| `record/` | Record、Note、Diary/Block、Bookmark、FileRecord、CardField、ContentTemplate | 记录主体与类型扩展一起保存 |
| `organization/` | Folder、Tag、EntityTag、Project/Link、EntityRelation | 多态引用统一校验类型、owner 和有效性 |
| `attachment/` | Attachment、AttachmentLink | 元数据与多处引用；原件在文件目录 |
| `plan/` | Task/Subtask/Group、Event、RepeatRule、Occurrence | 规则与单次实例分开，按原实例键去重 |
| `habit/` | Habit、HabitRuleVersion、HabitLog、HabitPause | 新规则不改变历史目标 |
| `focus/`、`goal/` | FocusSession/Segment；Goal/Progress/SourceLink/Milestone | 有效时长和进度来源可核对 |
| `ledger/` | Ledger、Category、Account、Transaction、AccountEntry、TransactionTemplate、Budget/Alert、ReimbursementClaim/Item、ImportBatch/Row | 财务写入统一事务；余额从期初值与分录计算 |
| `payment/` | Subscription、BillPlan、PaymentPlanVersion、PaymentPeriod、PaymentSettlement | 订阅/缴费共用期间和结算规则 |
| `life/` | Checklist/Item、Anniversary、Item/Category、StorageLocation、Maintenance、Loan/Return、CalculationHistory | 物品数量、归还数量、日期和历史约束 |
| `system/` | ReminderRule/Job、NotificationHistory、Draft、SearchIndex/History、BackupJob、ChangeLog | 草稿不参与统计，索引可重建，日志不泄露私密正文 |

领域目录名和类名分开：例如 `life/ItemEntity.kt` 表示物品，`life/ChecklistItemEntity.kt` 表示清单条目，避免同名混淆。

简单偏好 `AppPreference`、`PrivacyPreference` 是逻辑设置模型，实际由 `data/preferences/` 的 DataStore 保存；首页卡片布局、快捷入口等结构化配置放 Room。同一设置只有一个权威存储位置。

### 4.2 必须准备的关键文件

| 文件或目录 | 内容与要求 |
| --- | --- |
| `DailyLifeDatabase.kt` | 实体、版本、DAO，启用 schema 导出；初版从 version 1 开始 |
| `migration/Migration1To2.kt` 等 | 发布后每次结构变化的迁移；旧版本结构 JSON 不覆盖修改 |
| `migration/DatabaseIndexes.kt` | 条件唯一索引等 Room 声明不能完整表达的 SQL；新建库和迁移都执行相同约束 |
| `preferences/UserPreferences.kt` | 主题、字号、金额隐藏、备份提示等有类型的设置 |
| `preferences/PreferencesRepository.kt` | DataStore 读写、默认值、可迁移设置白名单 |
| `files/AttachmentStore.kt` | 应用内部路径、流式复制、大小和校验值 |
| `files/AttachmentShareProvider.kt` | 组织 FileProvider 临时授权，不暴露全部内部目录 |
| `files/OrphanFileCleaner.kt` | 只清理确认无引用且无在途操作的文件 |
| `service/LedgerWriteService.kt` | 交易、分录、付款关系、更正与日志的统一事务实现 |
| `reminder/ReminderScheduler.kt` | 到时提醒排程接口，允许测试替身 |
| `reminder/AlarmReminderScheduler.kt` | AlarmManager 具体实现与权限降级 |
| `reminder/ReminderReceiver.kt` | 到时重新核对对象后发出通知，不直接做长任务 |
| `reminder/ReminderRescheduleReceiver.kt` | 重启、时区/时刻等变化后触发重新排程 |
| `worker/OccurrenceRefreshWorker.kt` | 幂等补齐未来周期实例 |
| `worker/MaintenanceWorker.kt` | 回收站到期检查、孤立文件清理等可延迟工作 |

数据库约束至少落实：每天一篇有效日记、重复实例键唯一、每期账单唯一、同一期只有一份有效结算、有效非空交易关联唯一、同一外部账目不重复导入。累计退款/报销/归还上限在事务内重新检查，不能只在表单层检查。

### 4.3 手机里的实际文件结构

以下是 Android 管理的应用私有目录的相对布局，与电脑上的源代码目录不同：

```text
databases/
  daily_life.db                       Room 数据库及其运行时辅助文件
files/
  datastore/user_preferences.preferences_pb
  attachments/<附件UUID>/original.<安全扩展名>
  staging/import/<操作UUID>/           正在导入的文件与恢复信息
no_backup/
  maintenance/<操作UUID>/              备份/恢复工作区、切换日志与回退材料
cache/
  thumbnails/                         可再生成的缩略图
  previews/                           临时预览与分享副本
```

通过 `filesDir`、`cacheDir`、`noBackupFilesDir` 等 API 定位，不硬编码手机系统路径。`staging` 不放 cache，防止正式提交前被系统当缓存清理；维护工作区仍受磁盘空间和主动清理控制。

附件流转为：复制到 staging → 检查大小和校验值 → 移到稳定原件路径 → 数据库事务写元数据与引用 → 成功。数据库提交失败或进程中断后，通过导入状态核对，清理没有引用的残留；数据库事务不能替代文件系统的恢复处理。

删除文件前检查正式内容、回收站、草稿及正在进行的备份/恢复引用。只因当前页面看不到文件不能删除原件。[应用内部文件](https://developer.android.com/training/data-storage/app-specific)

## 5 页面与业务怎样连接

### 5.1 普通保存：以新建任务为例

```text
TaskEditorScreen 用户输入
  → TaskEditorViewModel 更新 UiState，保存 Draft
  → 点击保存，校验必填、日期和关联
  → TaskRepository.save(command)
  → DataWriteCoordinator 协调写入
  → Room 事务：Task + Subtask + 标签/提醒配置 + 删除对应草稿
  → 提交成功，更新页面状态
  → Repository 的 Flow 推送新结果
  → 任务列表、今天页、专题引用自动刷新
```

数据库提交后，再根据提醒规则安排系统提醒；排程失败显示“任务已保存，提醒待处理”，不能把已经成功的任务重新保存一遍。提醒中心可重试和核对实际状态。

- 输入为空、保存中、保存失败、保存成功分别表达；失败保留表单，成功后才关闭。
- `StateFlow<UiState>` 对外只读，页面按生命周期订阅；表单的业务草稿落 Room，返回栈状态不代替持久保存。
- 防重复使用稳定操作编号、原实体编号和数据库约束；按钮禁用只是体验补充。
- 编辑命令带预期 `revision`，发现已被其他入口修改时重新核对，不覆盖较新数据。
- `DataWriteCoordinator` 在外层写入入口获取一次协调锁，内部服务不重复获取同一非重入锁；Worker 和 Receiver 发起的写入也遵守同一规则。

### 5.2 财务保存：以缴费并记支出为例

```text
BillDetailScreen 确认金额、日期、账本、分类、账户
  → SettlePaymentUseCase
  → LedgerRepository.settlePayment(command)
  → LedgerWriteService 在同一 Room 事务内
      核对期间、账户、金额、是否已结算
      写 Transaction + AccountEntry + PaymentSettlement + ChangeLog
  → 提交后统一刷新期间状态、余额、账本与统计
```

订阅付款、缴费付款、维修记账、退款、报销、转账和导入账单都通过同一个财务写入实现。生活模块的仓库管理计划资料，不自行插入支出或改余额。

“仅确认付款，不记账”也保存 `PaymentSettlement`，其 `transaction_id` 为空。修改、撤销和重试必须遵循同一规则；不能让“已付状态”和实际交易各自修改。余额以期初值和有效分录计算，缓存可以重建。

### 5.3 导航与页面状态

- 五个入口各保留列表筛选、滚动和返回位置；“我的”从头像进入，不增加第六个底部入口。
- 页面键仅携带对象类型、编号和必要来源信息，不携带整篇正文、文件原件或可变数据库实体。
- 快捷新增保存后回到来源；取消有草稿提示。详情对象被删除时展示明确状态，不崩溃。
- 通知跳转先经过应用锁，再查当前对象；已删除、已完成或已取消的提醒不跳进失效编辑页。
- 导航使用 Navigation 3 的页面键与返回栈机制，按选定版本实现状态保存。[Navigation 3](https://developer.android.com/guide/navigation/navigation-3)

## 6 备份与恢复的文件组织

### 6.1 开发文件

```text
data/backup/
├─ BackupManager.kt                  导出任务编排、进度、取消
├─ RestoreManager.kt                 预览、冲突和恢复编排
├─ BackupSnapshotExporter.kt         生成一致的业务和附件快照
├─ BackupArchiveWriter.kt            写临时包与用户选定目标
├─ BackupArchiveReader.kt            安全读取、大小限制、路径检查
├─ BackupValidator.kt                版本、数量、校验、引用和财务一致性
├─ RestoreCommitter.kt               切换、恢复日志、失败回退
├─ format/
│  ├─ BackupManifest.kt              备份格式和清单
│  ├─ BackupSettings.kt              可迁移设置白名单
│  └─ v1/                           第一版 JSON 导出对象，不暴露 Room 实体
└─ migration/                       旧备份格式到当前格式的转换
```

### 6.2 用户导出的备份包

```text
daily-life-backup_<日期时间>.zip
├─ manifest.json                     格式/应用/数据库版本、范围、数量、校验清单
├─ data/
│  ├─ profile.json
│  ├─ records.json
│  ├─ organization.json
│  ├─ plans.json
│  ├─ habits-focus-goals.json
│  ├─ ledger.json
│  ├─ payments.json
│  ├─ life.json
│  └─ system.json                    可迁移提醒规则、必要日志等
├─ attachments/<附件UUID>/original.<安全扩展名>
└─ settings.json                     外观和可迁移偏好
```

每个领域 JSON 按表/对象集合分组，保留原 UUID、关联和未清理回收站。清单记录除 manifest 本身以外的各数据文件和原件的长度与 SHA-256、各类对象数量、备份格式版本；格式版本与数据库版本分别管理。

不导出草稿、缓存、搜索索引、设备密钥、系统通知编号；搜索/计算历史默认不导出。导出前提示未提交草稿。普通 ZIP 是明文备份；后续若提供口令加密，另定义可识别的加密格式和恢复流程。

### 6.3 一致性与恢复要求

1. 导出开始时进入可见的维护状态，暂缓业务写入和文件清理；所有仓库与 Worker 服从协调器。取同一份数据库快照并复制其引用原件，快照完成再放开写入。
2. 在私有工作区打包、校验，再通过系统选择器写到用户选定位置。取消或写入失败不得显示备份成功；记录不完整输出的情况。
3. 读备份先校验格式、空间、条目数量、长度与校验值；阻止绝对路径、目录越界、重复路径和异常解压量。较新且不支持的格式停止导入，不尝试清库。
4. 覆盖恢复前，先生成并验证当前数据的独立回退备份；在临时数据库和临时附件目录中恢复、校验，当前库保持可用。
5. 切换前停写并关闭数据库；使用维护日志记录数据库、附件、设置的切换阶段。它们跨文件不能视为一个原子事务，必须支持启动时继续或回退；旧副本在验证成功前保留。
6. 合并恢复按 UUID 识别对象，同内容跳过；冲突选择应连同分录和依赖一起处理。财务冲突不能产生两份生效交易，不能只按修改时间静默覆盖。
7. 完成后重建索引、余额缓存与统计，核对金额、引用和日记唯一性；检查通知权限，仅按用户确认重新安排有效未来提醒。

开发顺序为“完整导出 → 覆盖恢复 → 合并恢复”，尚未验证的恢复方式不向日常使用者开放。完整功能交付时仍需覆盖 V2.0 的合并和跨本地资料处理规则。备份存到本机文档/U 盘/电脑；系统选择器可能显示云盘，是否选择由用户决定，应用不自动上传。[系统文件选择器](https://developer.android.com/training/data-storage/shared/documents-files)

## 8 实际开发步骤

### 8.1 第一次创建工程

1. Android Studio 新建支持 Compose 的 Empty Activity 工程，保存到 `D:/desktop/myapp/daily-life-android`，语言选 Kotlin。
2. 确定应用名、正式包名、最低系统；配置 Gradle JDK 和 SDK 路径。`local.properties` 可使用 `sdk.dir=E:/AndroidSDK`，不提交本机路径。
3. 对齐第 7 章工具链；建立版本目录、`app` 单模块及基础源码目录。第一次空工程构建成功后记录基线。
4. 建立 `DailyLifeApplication`、`AppContainer`、主题、五入口与导航，设置页由头像进入；页面先允许空数据。
5. 接入 Room、KSP、schema 导出、DataStore；创建 `LocalProfile` 和首个任务模型。数据库按版本迁移，不开启破坏式重建兜底。
6. 接入一套基础错误反馈、表单草稿和回收站规则；打通任务创建、修改、完成、删除、恢复及重启查看。
7. 再实现随记、基础记账和附件；尽早完成完整备份与覆盖恢复，验证后才开始在正式版长期录入个人数据。

### 8.2 每新增一个功能的固定顺序

| 步骤 | 做什么 | 应产出的文件或结果 |
| --- | --- | --- |
| 1 明确功能 | 从 V2.0 取字段、默认值、必填、边界和验收项 | 功能待办与已确认的输入规则 |
| 2 确定数据 | 检查能否复用既有表；定义关系、索引、删除规则 | Entity、DAO、必要 migration 和 schema |
| 3 写保存规则 | 金额、日期、归属、幂等、事务和冲突处理 | Repository，必要 UseCase/Service |
| 4 做页面 | 列表、详情、编辑，补齐空/错/保存中状态 | Route、Screen、ViewModel、UiState |
| 5 接公共能力 | 草稿、标签、附件、搜索、提醒、回收站 | 对应公共入口和状态刷新 |
| 6 接备份 | 新模型加入导出对象、校验、恢复、版本转换 | Backup DTO、数量与引用检查 |
| 7 验证交付 | 规则测试、保存后重启、覆盖更新、相关跨模块流程 | 测试结果及功能进度更新 |

增表不能只实现页面和 DAO：必须同时考虑迁移、导出恢复、删除恢复、搜索和关联。未完成的入口不显示“保存成功”或使用假数据冒充正式数据。

### 8.3 分阶段完成什么

| 阶段 | 本阶段交付 | 进入下一阶段前的要求 |
| --- | --- | --- |
| 1 工程与基础 | 正式工程、五入口、主题、导航、Room、DataStore | 构建安装成功，基础数据重启后存在 |
| 2 首个完整业务 | 任务、随记、基础收支、账户、草稿、回收站 | 三个主要入口读取同一份真实数据，金额正确 |
| 3 数据可恢复 | 附件、搜索、完整导出、覆盖恢复、签名与迁移 | 恢复后数量、原件、关联和余额一致 |
| 4 计划与财务完善 | 日程、周期、习惯、专注、目标、转账、退款、报销、预算、账单导入 | 周期不重复，累计额度正确，提醒可核对 |
| 5 生活工具 | 清单、纪念日、订阅、缴费、物品、借还、专题、计算，完善记录类型 | 跨模块关联与付款使用统一规则 |
| 6 完整个人版 | 合并恢复、隐私、统计、性能、全功能验收 | V2.0 全部范围逐项核对，真实手机更新与恢复通过 |

阶段用于控制顺序，不删除完整设计中的模块。每次只交付一个可以真实保存、查找、修改和恢复的功能闭环。

```powershell
# 将实际设备编号替换为 adb devices 显示的目标
$taskDeviceSerial = '<实际设备编号>'
adb -s $taskDeviceSerial install -r '.\app\build\outputs\apk\debug\app-debug.apk'
```

手机型号、系统版本、通知开关和电池限制以真实设备验证。测试删除、覆盖恢复和异常数据时使用调试版虚构数据，不在正式个人资料上试验。

### 9.3 自用正式包

1. 在工程外创建并妥善保存正式签名密钥，备份密钥和密码；本机签名配置不进入版本控制。
2. 固定正式包名和签名。调试版与正式版分开使用；长期个人数据从已验证的正式签名版本开始。
3. 每次更新递增 `versionCode`、填写 `versionName` 和变更说明；结构变化带 Room 迁移和测试。
4. 使用 Android Studio 的 Generate Signed App Bundle / APK 生成签名 APK；只在自己手机安装时可以分发 APK，无需先建服务器或上架。
5. 配置完本机 release 签名后也可运行 `:app:assembleRelease`，检查最终包已正确签名，再安装验证。
6. 更新前导出完整备份；用同包名、同签名的较新版本覆盖安装，核对数据。不要先卸载旧版，卸载会删除应用内部数据。

开启压缩后需要用实际 release 包复核序列化、导航、数据库、文件分享和提醒。保存该版本的安装包、版本说明及必要的混淆映射，便于定位问题；旧安装包不保证能直接读取升级后的数据库。[Android 应用签名](https://developer.android.com/studio/publish/app-signing)

### 10.2 每个功能完成的标准

- 字段要求、默认值、选填/条件必填和错误提示与 V2.0 一致；编辑失败保留输入。
- 新增、查看、修改、删除、恢复在断网下可用；关闭重开和进程重建后数据正确。
- 今天、日历、专题和财务摘要读取原对象，修改后相关入口同步刷新。
- 已提交操作重试不重复记账或生成实例；财务不出现交易、分录、缴费状态只成功一部分。
- 新数据类型已经接入搜索、附件引用检查、完整备份、恢复和数据库迁移。
- 权限拒绝、附件缺失、空间不足、通知受限、导出中断时，给出明确状态和可执行的重试方式。
- 真实手机完成安装、覆盖更新、通知、文件导入导出和备份恢复；模拟器通过不替代真机通过。
- 更新工程 README 的完成/待做状态，按 V2.0 第 9 章 A01–A30 验收记录结果。

开始日常使用前，至少通过“建立记录 → 导出完整备份 → 在独立测试环境恢复 → 核对条目、附件与余额 → 同签名覆盖更新”的完整验证。
